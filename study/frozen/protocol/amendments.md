# Поправки протокола: версия 1.1 (проект)

База: файл 02, протокол v1.0 (2 модели, ручное выполнение в чатах, 144
испытания / 288 запросов). Все изменения ниже — уточнения версии 1.1; они не
приписываются исходным статьям и не меняют научные решения файла 02.

## Принятые изменения

1. **Выборка: 2 → 7 семейств.** OpenAI, Anthropic, Google, Kimi, GLM,
   DeepSeek, Qwen — по одной новейшей универсальной текстовой модели на
   семейство по каталогу OpenRouter на дату исполнения (этап 02), с
   фиксацией после пилота (этап 04). Объём: 504 испытания / 1008 основных
   генераций. Индексы моделей — в порядке пользователя (M1…M7).
   Пользовательская таблица кандидатов сохранена как неверифицированный ввод:
   `study/models/user_candidate_table.md`.

2. **API-исполнение вместо ручных чатов.** OpenRouter Chat Completions;
   каждое испытание — независимая история; ход 2 получает
   `[user: ход 1, assistant: реальный ответ 1, user: назначенный ход 2]`.
   Один конкретный model ID; фиксированный provider/endpoint
   (`provider.only`, `allow_fallbacks=false`, `require_parameters=true`);
   без `auto`/`latest`/fallback-цепочек; без системных наставлений, если
   endpoint их не требует (иначе — единое нейтральное сообщение для всех
   моделей, отдельная поправка до пилота).

3. **Вторичные настройки (уточнение v1.1).** temperature=0.7 там, где
   поддерживается, иначе документированный штатный режим — фиксируется по
   модели одинаково во всех условиях. Reasoning — документированный штатный
   режим выбранного релиза; `reasoning.exclude=true` не отключает
   вычисление/оплату reasoning. Лимиты вывода подбираются техническим
   пилотом, не по эффекту. Seed генерации не задаётся (seed правила —
   только для расписания). Отключение кеша ответов —
   `X-OpenRouter-Cache: false`, если подтверждено актуальной документацией
   на этапе 03.

4. **Пилот расширен на 7 моделей.** 4 двухходовых испытания на модель
   (по одному на условие) = 28 испытаний / 56 генераций; сценарий
   CASE-PILOT (файл 02, «4–8 пробных запусков» на отдельной ситуации).
   Это явное расширение процедуры пилота, зафиксированное здесь. Тексты
   пилота составлены по шаблону основных стимулов (см. `source_map.md`).

5. **Расписание.** Правило файла 02 сохранено (3 волны; seed = 220926 +
   100 × номер модели + волна; равномерное чередование моделей), таблица
   пересоздаётся для 7 моделей на этапе 04 — готовая таблица файла 02
   покрывает только M1/M2.

6. **Учёт стоимости и состояния.** Журнал попыток в устойчивом хранилище
   (JSONL/SQLite в `study/data/`), резервирование стоимости до отправки,
   лимит `MAX_BUDGET_USD` общий на пилот + основной сбор + повторы,
   resume без повторной оплаты завершённых ходов.

## Что не меняется

- Русские стимулы, ключи, коды B/F/G/A/V/P/W, гипотезы H1–H3 и контрасты —
  дословно из файла 02.
- Модули A–D не запускаются. Сокращённый вариант (48 испытаний) файла 02
  не выбирается: объём v1.1 зафиксирован пользователем как 3 повтора.
- Никаких побудок к «честности» в стимулах, системных наставлений о цели
  исследования, передачи гипотез/ключей испытуемым.


## A-04 (2026-09-22, до сбора) — сокращение повторов под лимит бюджета

Решение пользователя: общий расход ≤ $5 (`MAX_BUDGET_USD=5`,
`REPETITIONS=1`). Применён заранее предусмотренный протоколом вариант
(DOCX-02, P0030): «один повтор» — демонстрационный объём.

- Основной сбор: 7 моделей × 6 сценариев × 4 условия × 1 повтор =
  **168 испытаний / 336 генераций** (было 504/1008 при 3 повторах).
- Пилот без изменений: 28 испытаний / 56 генераций.
- В ячейке «модель × условие» теперь 6 испытаний (по одному на сценарий),
  а не 18 — все знаменатели и ограничения отражают это в отчётах.
- Оценка (официальные endpoint'ы, reasoning-сценарии): low $2.57 /
  expected $6.03 / high $13.90 против лимита $5. Expected-сценарий не
  вписывается; фактический расход reasoning будет измерен пилотом, после
  чего гейт этапа 05 примет решение по реальным данным. Жёсткий лимит $5
  делает превышение невозможным — при нехватке сбор остановится в PARTIAL.
